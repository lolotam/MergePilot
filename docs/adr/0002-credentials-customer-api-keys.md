# ADR-0002: المفاتيح — مفاتيح API يملكها العميل، وطبقة CredentialStore

- **الحالة:** Accepted (صاحب المشروع، 2026-10-11)
- **مرتبط بـ:** PRD v0.2 §5، ADR-0004

**تحديث 2026-10-13:** [ADR-0019](0019-dashboard-subscription-auth.md) بيضيف الاشتراكات وpi-ai. الـ App دلوقتي بيستخدم خزنة AES-256-GCM؛ `CredentialStore` وبيانات `info()` غير السرية لسه نفس الواجهة. فقرة API-only وتنفيذ الـ App لاحقًا أدناه بتصف القرار الأول.

## السياق

حلّلنا ٣ مستودعات مرجعية. كلهم بيخزنوا التوكنات كنص مكشوف (YAML أو JSON)، وبعضهم بيقرا ملفات تسجيل أدوات تانية، وكلهم بيشغّلوا اشتراكات المستهلكين.

في نفس الوقت، Harness عنده فكرتين كويسين:

- **واجهة مفاتيح مابترجّعش القيمة** (`CredentialInfo`).
- **مسار كتابة واحد مقفول** (`modifyRecord`).

## القرار

1. **الإصدار الأول بيستخدم مفاتيح API بس:** `ANTHROPIC_API_KEY` و`OPENAI_API_KEY` و`GEMINI_API_KEY`. المفاتيح بتيجي من GitHub Secrets عن طريق متغيرات البيئة.
2. المحرك بيطلب المفتاح من `CredentialStore` بس، وده ليه عمليتين:
   - `info()`: بترجّع بس «موجود / مصدره».
   - `resolve()`: بترجّع القيمة لاستدعاء واحد مصرّح بيه.
3. **تنفيذ الـ Action:** `EnvCredentialStore`.
4. **تنفيذ الـ App بعدين:** مخزن متشفر بـ envelope encryption عن طريق KMS، ومعزول لكل مؤسسة.
5. **ممنوع:**
   - قراءة `~/.claude` أو keychain أو `~/.aws` أو ADC على جهاز مشترك.
   - أي ملف توكنات محلي في الإصدار الأول.
   - كتابة أي سر في log، أو خطأ، أو prompt.

## النتائج

- سطح الهجوم صغير جدًا في الإصدار الأول.
- الفاتورة بتروح لصاحب المفتاح مباشرة.
- لما الـ App ييجي، هيضيف تنفيذ جديد لنفس الواجهة، والمحرك مش هيتغير.
