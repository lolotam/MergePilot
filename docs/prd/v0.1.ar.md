## 1. فكرة المنتج

تطبيق GitHub يراجع التغييرات المقترحة قبل دمجها في المشروع، ويكتب ملخصًا وملاحظات بجانب الأسطر المعنية، بأسلوب قريب من تجربة CodeRabbit.

يختار صاحب المشروع مزود الذكاء الاصطناعي: OpenAI أو Claude أو Gemini. يعمل المنتج بمحرك مستقل، بحيث يمكن إضافة مزود أو تغييره دون إعادة بناء نظام مراجعة GitHub.

**القيمة الأساسية:** اكتشاف أخطاء مهمة، شرحها بوضوح، وتقليل وقت المراجعة مع التحكم في تكلفة الاستخدام وخصوصية الكود.

مصطلحات مبسطة:

- **PR:** مجموعة تغييرات يطلب المطور مراجعتها قبل دمجها.
- **API key:** مفتاح يسمح لتطبيقنا باستخدام خدمة الذكاء الاصطناعي.
- **OAuth:** تفويض عبر صفحة المزود، دون إدخال كلمة المرور في تطبيقنا.
- **Webhook:** إشعار يرسله GitHub عند إنشاء PR أو تحديثه.
- **Inline comment:** ملاحظة تظهر بجانب سطر محدد من الكود.

## 3. ما تحققنا منه في DeepSeek Harness

فُحص المستودع عبر تطبيق GitHub المتصل. النسخة المرجعية:

### نتائج موثقة من المصدر

1. المستودع موجود، ويصف نفسه بأنه Harness يعتمد على الإضافات. المشروع في مرحلة Developer Preview، ويعلن احتمال تغييرات تكسر التوافق. [README](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/README.md)

2. ترخيص الكود الأساسي MIT. يسمح بالاستفادة من الكود وفق شروط الترخيص، ومنها إبقاء إشعارات الحقوق عند نسخ أجزاء منه. الترخيص لا يمنح إذنًا لاستخدام خدمات المزودين خارج شروطهم. [LICENSE](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/LICENSE)

3. توجد إضافة `llm-pi-ai` تعتمد على الحزمة `@earendil-works/pi-ai`، ويحدد ملفها نطاق إصدار `^1.0.2`. [ملف الحزمة](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/packages/llm/llm-pi-ai/package.json)

4. الإضافة تسجل مسارات تسجيل الدخول التي توفرها مكتبة المزود، وتنقل رسائل التفويض إلى واجهة Harness. لكنها تستبعد OAuth للمزود ذي المعرف `openai` بسبب عدم توفير معرّف التثبيت المطلوب. هذا الاستثناء لا يعني استبعاد `openai-codex`، وهو معرف مختلف. [login.ts](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/packages/llm/llm-pi-ai/src/login.ts)

5. تخزن طبقة المصادقة بيانات التفويض كسجل مستقل، وتتيح تحديثه داخل عملية تعديل مقفلة لتجنب تعارض عمليات التجديد المتزامنة. اسم `llm-pi-ai` هنا نطاق تخزين داخلي، وليس OAuth scope. [auth.ts](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/packages/llm/llm-pi-ai/src/auth.ts)

6. مخزن الأسرار المحلي يستخدم ملف YAML. توضح وثائقه أن العمليات التي تعمل بنفس مستخدم نظام التشغيل يمكنها قراءته؛ لذلك ليس حدًا أمنيًا مناسبًا لعزل أسرار خدمة SaaS عن أدوات الوكيل. [المخزن المحلي](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/packages/credentials/credentials-local/README.md)

**قرار المنتج:** نستفيد من فصل المزود والمصادقة والتخزين، ونصمم مخزن أسرار وعزلًا يناسبان منتجنا.

### ما لم يثبت بعد

- لم تُنفذ الإضافات، ولم تُجرّب تسجيلات الدخول أو صلاحية الرموز.
- لم يُثبت الإصدار الدقيق المحلول داخل ملف قفل الاعتماديات.
- فحص مكتبة `pi` أدناه يتعلق بمصدرها الحالي، وليس إثباتًا أن Harness يشحن النسخة نفسها.
- لا تُعد هذه المراجعة تدقيقًا أمنيًا شاملًا أو موافقة تجارية من المزودين.

## 4. تدفقات الاشتراك الموجودة فعلًا

المكتبة الخارجية موجودة في [earendil-works/pi](https://github.com/earendil-works/pi). النسخة الحالية المسجلة أثناء الفحص:

`ea448f454af474f3e2fe9733b331e17b0662f5d6`

### Claude عبر مكتبة pi

المصدر يتضمن تسجيل دخول لاشتراك Claude Pro/Max:

- يفتح صفحة تفويض لدى Claude.
- يستخدم Authorization Code مع PKCE من نوع S256.
- يستقبل النتيجة عبر callback محلي أو إدخال رمز يدوي.
- يبدل رمز التفويض إلى access token وrefresh token.
- يحسب انتهاء الصلاحية مع هامش خمس دقائق.
- يجدد الرموز باستخدام refresh token.

الصلاحيات المكتوبة في المصدر تشمل:

`org:create_api_key`، `user:profile`، `user:inference`، `user:sessions:claude_code`، `user:mcp_servers`، `user:file_upload`.

هذه صلاحيات واسعة بالنسبة إلى منتج يراجع PRs فقط. وجودها في مكتبة مفتوحة المصدر لا يجعل استخدامها داخل تطبيقنا معتمدًا. [مصدر Claude OAuth](https://github.com/earendil-works/pi/blob/ea448f454af474f3e2fe9733b331e17b0662f5d6/packages/ai/src/auth/oauth/anthropic.ts)

### Codex عبر مكتبة pi

المصدر يتضمن تسجيل اشتراك ChatGPT لمسار Codex:

- Authorization Code مع PKCE، أو مسار device code.
- callback محلي لمسار المتصفح.
- الصلاحيات: `openid profile email offline_access`.
- تخزين access token وrefresh token ووقت الانتهاء ومعرف الحساب.
- تجديد باستخدام refresh token.

المكتبة تحمل client ID ثابتًا. [مصدر Codex OAuth](https://github.com/earendil-works/pi/blob/ea448f454af474f3e2fe9733b331e17b0662f5d6/packages/ai/src/auth/oauth/openai-codex.ts)

### Gemini في المصدر المفحوص

مزود `google` يستخدم مفتاح Gemini API. مزود `google-vertex` يتضمن مسارات Google Cloud credentials وADC. لم نجد في الملفات المفحوصة دليلًا على أن اشتراك Gemini الاستهلاكي يموّل محرك PR عام. [مزود Gemini](https://github.com/earendil-works/pi/blob/ea448f454af474f3e2fe9733b331e17b0662f5d6/packages/ai/src/providers/google.ts)، [مزود Google Cloud](https://github.com/earendil-works/pi/blob/ea448f454af474f3e2fe9733b331e17b0662f5d6/packages/ai/src/providers/google-vertex.ts)

## 5. سياسة المصادقة الرسمية

**المبدأ:** موافقة المستخدم على تسجيل الدخول لا تكفي وحدها؛ يجب أن يسمح المزود لتطبيقنا بهذا الاستخدام، وللواجهة التي سنستدعيها، ولنمط الاستضافة والفوترة.

| الخدمة | المسار المخطط | موقف رموز الاشتراك |
|---|---|---|
| OpenAI | مفتاح Platform API في الإصدار الأول | OAuth الرسمي داخل Codex موثق؛ لا نعامل رموزه كتصريح عام لتطبيقنا |
| Claude | مفتاح Claude API يملكه العميل | لا نجمع رموز Claude.ai أو نعيد استخدامها داخل محركنا |
| Gemini | مفتاح Gemini API | لا نعتمد على اشتراك Gemini الاستهلاكي |
| Gemini عبر Google Cloud | هوية خدمة رسمية؛ OAuth مفوض عند الحاجة | مسار Cloud مستقل يتطلب مشروعًا وصلاحيات وفوترة مناسبة |
| GitHub | GitHub App بصلاحيات مستودعات محددة | رموز تثبيت رسمية للوصول إلى المستودعات |

OpenAI يفصل فوترة ChatGPT عن فوترة API. تسجيل الاشتراك داخل Codex مسار رسمي لذلك المنتج، ولا يثبت السماح بإعادة توجيه رموزه إلى خدمة مستقلة. [الفوترة](https://help.openai.com/en/articles/9039756-managing-billing-for-chatgpt-and-the-api-platform)، [مصادقة Codex](https://developers.openai.com/codex/auth/)

وثائق Anthropic تمنع تقديم تسجيل Claude.ai داخل تطبيق طرف ثالث وجمع رموز جلساته أو تمريرها. تسمح بحالات محددة لتشغيل Claude Code الأصلي غير المعدل؛ هذه حالة مختلفة عن محركنا. [المصادقة والامتثال](https://code.claude.com/docs/en/legal-and-compliance)

**قرار الإصدار الأول:** مفاتيح API يملكها العميل، مع دعم Google Cloud الرسمي في مرحلة لاحقة. (تعديل س45: OAuth برقم تعريف أداة رسمية مسموح بقرار صاحب المشروع، من غير ما يحتاج تسجيل عميل باسمنا.)

لا يدخل في النطاق:

- استخراج الرموز من أدوات مثبتة أو متصفح المستخدم.
- نسخ ملفات تسجيل دخول Claude Code أو Codex.
- تدوير الحسابات لتجاوز حدود الاشتراك.

## 6. نطاق الإصدار الأول

### مطلوب

- تثبيت GitHub App على مستودعات يحددها المستخدم.
- دعم OpenAI وClaude وGemini عبر مفاتيح API.
- اختيار مزود ونموذج لكل مستودع.
- مراجعة PR عند إنشائه أو تحديثه أو انتقاله من Draft إلى جاهز للمراجعة.
- ملخص للمراجعة وتعليقات على أسطر صالحة في التغييرات.
- التركيز على أخطاء الصحة البرمجية، الأمان، وفقدان البيانات.
- ميزانية لكل مراجعة وحد شهري.
- سجل لحالة المراجعة والتكلفة، دون أسرار.
- إعداد ملفات مستبعدة، ولغة الملاحظات، وشدة المشكلات المنشورة.
- إعادة محاولة الأعطال المؤقتة دون تكرار التعليقات.

### مؤجل

- تعديلات تلقائية للكود ودمج PRs.
- تشغيل كود PR أو أوامره.
- محادثة عامة داخل GitHub.
- فهرسة المستودع كاملًا.
- مقارنة آراء عدة نماذج في كل مراجعة.
- متجر إضافات مفتوح.
- تسجيل دخول باشتراكات استهلاكية.
- فوترة استخدام Claude نيابة عن العملاء قبل حسم الشروط التجارية.

## 7. رحلة المستخدم

1. **ربط GitHub:** يختار المستودعات التي يسمح للتطبيق بمراجعتها.
2. **اختيار المزود:** يرى طريقة الاتصال والتكلفة المتوقعة وسياسة إرسال الكود.
3. **إضافة المفتاح:** يضيفه إلى حقل آمن؛ يظهر بعد الحفظ كمفتاح مخفي.
4. **اختبار الاتصال:** طلب صغير يوضح نجاح الاتصال أو سبب الفشل.
5. **ضبط المراجعة:** يختار النموذج، اللغة، الملفات المستبعدة، والميزانية.
6. **مراجعة تجريبية:** يعاين النتائج قبل تفعيل النشر التلقائي.
7. **التفعيل:** ينشر التطبيق الملاحظات داخل GitHub.
8. **الإيقاف:** يمكن تعطيل المستودع أو حذف اتصال المزود.

اللغة الافتراضية لواجهة المنتج عربية، مع خيار الإنجليزية. لغة التعليقات قابلة للاختيار لكل مستودع.

رسائل الحالة واضحة: «جارٍ الانتظار»، «جارٍ التحليل»، «اكتملت المراجعة»، «تجاوزت الميزانية»، «يحتاج الاتصال إلى تحديث»، «تغير PR؛ سنراجع النسخة الجديدة».

## 8. مراجعات GitHub والتعليقات

التسلسل المطلوب:

**إشعار GitHub ← التحقق منه ← مهمة مراجعة ← قراءة التغييرات ← تحليل المزود ← التحقق من الملاحظات ← النشر**

متطلبات التكامل:

- التحقق من `X-Hub-Signature-256` على جسم الطلب الأصلي، قبل معالجة محتواه.
- حفظ المهمة في طابور دائم قبل تأكيد استقبالها.
- استخدام `X-GitHub-Delivery` لمنع معالجة الإشعار المكرر.
- ربط المهمة بمعرف المؤسسة والتثبيت والمستودع وPR ونسخة `head SHA`.
- التأكد من صلاحية التثبيت للمستودع قبل القراءة وقبل النشر.
- إلغاء النتائج القديمة إذا وصل commit أحدث.
- احترام الترقيم متعدد الصفحات وحدود GitHub.
- عدم اعتبار patch المفقود أو المبتور مراجعة مكتملة.
- استبعاد الملفات الثنائية والمولدة وملفات الأسرار.

صلاحيات التطبيق المقترحة:

| الصلاحية | المستوى | الغرض |
|---|---|---|
| Metadata | قراءة | تعريف المستودع |
| Contents | قراءة | سياق الكود |
| Pull requests | قراءة وكتابة | قراءة PR ونشر المراجعات |
| Checks | مؤجلة | عرض حالة عبر Check Run لاحقًا |

لا نطلب كتابة Contents أو إدارة المستودع. لا نحتاج Issues في الإصدار الأول لأن أوامر المحادثة ليست ضمن نطاقه.

كل ملاحظة منشورة تتضمن: المشكلة، أثرها، الدليل، واقتراح إصلاح. يفحص النظام المسار والسطر وموضعه في diff قبل النشر. إذا تعذر تثبيت موضعها، توضع في الملخص أو تُستبعد.

النشر يكون بصيغة `COMMENT`؛ لا يمنح التطبيق موافقة دمج ولا يرفض الدمج تلقائيًا.

مصادر التكامل: [التحقق من Webhooks](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries)، [مراجعات PR](https://docs.github.com/en/rest/pulls/reviews).

## 9. تصميم المحرك وواجهاته

هذا القسم يحدد عقودًا مستقبلية، ولا يتضمن كودًا تنفيذيًا.

| المكوّن | مسؤوليته |
|---|---|
| Provider Registry | قائمة المزودين والنماذج وطرق المصادقة المعتمدة |
| Credential Broker | جلب السر للطلب المصرح به فقط |
| Provider Adapter | تحويل الطلب إلى صيغة المزود وتوحيد النتيجة |
| Review Orchestrator | تشغيل مراحل المراجعة والتحكم في الوقت والميزانية |
| Findings Validator | التحقق من بنية الملاحظة ودليلها وموضعها |
| GitHub Publisher | نشر نتائج صحيحة دون تكرار |

### واجهة المزود

العمليات المطلوبة:

- `capabilities`: النماذج، الحدود، والمزايا المدعومة.
- `validateConnection`: اختبار الاتصال دون كشف السر.
- `estimateUsage`: تقدير الاستهلاك.
- `review`: تحليل سياق محدود وإرجاع نتائج منظمة.
- `normalizeError`: تحويل خطأ المزود إلى رسالة مفهومة.

المدخلات المشتركة: المزود، النموذج، اللغة، التغييرات، السياق، تعليمات المراجعة، حد الوقت، وحد المخرجات، ومرجع الاتصال.

المخرجات المشتركة: ملخص، قائمة ملاحظات، استهلاك فعلي أو تقديري، معرف الطلب، وحالة اكتمال المراجعة.

الملاحظة تحتوي: معرف، مسار، سطر، عنوان، شرح، شدة، دليل، واقتراح. ثقة النموذج مؤشر للفرز وليست احتمالًا مثبتًا لصحة الملاحظة.

### واجهة المصادقة

العمليات المطلوبة:

`connect`، `status`، `resolveForRequest`، `refreshIfNeeded`، `disconnect`.

- مفاتيح API تحتاج تبديلًا أو حذفًا؛ لا نعاملها كرموز OAuth قابلة للتجديد.
- OAuth يُفعّل لكل مزود على حدة بعد التحقق من الاعتماد.
- تحديث الرموز المتزامن يستخدم قفلًا وتحديثًا ذريًا.
- إلغاء التفويض يوقف الاستخدام ويطلب إعادة الربط.
- فشل الاتصال لا يؤدي إلى الانتقال الصامت إلى حساب أو مزود آخر.

## 10. الأمان والخصوصية

### حماية الأسرار

- تخزين مشفر باستخدام مدير أسرار أو KMS؛ لا يُحفظ مفتاح التشفير بجانب البيانات.
- إعدادات المستودع تحتوي مرجع الاتصال فقط.
- لا ترسل الأسرار إلى النموذج أو المتصفح بعد حفظها.
- عزل الأسرار حسب المؤسسة والاتصال.
- فصل خدمة GitHub عن خدمة استدعاء النماذج قدر الإمكان.
- إخفاء الأسرار من السجلات والأخطاء والنسخ الاحتياطية.
- حذف اتصال المزود يمنع الاستخدام فورًا؛ ويُوضح للمستخدم متى يلزم إلغاء المفتاح لدى المزود.

### OAuth الرسمي، عند إضافته

- عميل مسجل يخص تطبيقنا، أو رقم تعريف أداة رسمية بقرار صاحب المشروع (تعديل س45).
- PKCE حيث يدعمه المزود، و`state` عشوائي مستقل ومؤقت.
- callbacks مسجلة بدقة وربط المحاولة بالمستخدم والمؤسسة.
- أقل صلاحيات لازمة، دون توسيع تلقائي.
- رموز التجديد مشفرة ولا تظهر للواجهة.
- اتباع مكتبة المزود الرسمية للتجديد عندما تتوفر.
- Google Cloud يعتمد صلاحيات IAM إلى جانب OAuth؛ scope وحده لا يمنح وصول المشروع.

مرجع Google: [تفويض تطبيقات الويب](https://developers.google.com/identity/protocols/oauth2/web-server)، [مصادقة Google Cloud](https://cloud.google.com/vertex-ai/generative-ai/docs/start/gcp-auth).

### حماية الكود

- محتوى PR بيانات غير موثوقة، بما في ذلك تعليمات داخل التعليقات والملفات.
- لا تنفيذ للكود أو تنزيل اعتمادياته أثناء المراجعة.
- إرسال أقل سياق ممكن.
- فحص أسرار محتملة قبل الإرسال، مع حظر الملفات الحساسة افتراضيًا.
- منع الروابط وbase URLs غير المعتمدة في SaaS.
- عدم السماح لتعليمات الكود بتغيير سياسة المزود أو الميزانية أو صلاحيات النشر.
- عدم نقل الكود إلى مزود بديل دون إعداد صريح من المستخدم.

الاستضافة الذاتية لا تعني بقاء الكود داخل المؤسسة إذا كان المزود خارجيًا.

خصوصية Gemini تحتاج اختيار الخدمة والخطة بعناية؛ شروط الخدمة غير المدفوعة تحذر من إرسال المعلومات السرية، مع اختلافات إقليمية مذكورة في الشروط. يُحظر تفعيل مسار غير مدفوع لكود سري قبل مراجعة السياسة المناسبة. [شروط Gemini](https://ai.google.dev/gemini-api/terms)

## 11. خيارات الاستضافة والفوترة

| الخيار | الميزة | المسؤولية |
|---|---|---|
| استضافة ذاتية | تحكم أكبر في التشغيل والأسرار | المؤسسة تدير التحديثات والنسخ الاحتياطي |
| SaaS | إعداد وتشغيل أسهل | عزل العملاء، حماية المفاتيح، والالتزامات التجارية |
| SaaS مع عامل خاص لاحقًا | معالجة داخل شبكة العميل | تشغيل أعقد وتوزيع مسؤوليات إضافي |

**التوصية المبدئية:** تجربة أولى باستضافة ذاتية ومفاتيح يملكها العميل، ثم SaaS بعد إثبات الجودة وحسم شروط المزودين.

في مسار Claude، يظل الاستخدام مفوترًا لصاحب المفتاح وفق اتفاقه. أي تجميع للمفاتيح أو إعادة بيع للاستخدام يحتاج مراجعة تجارية مستقلة؛ وجود BYOK لا يعفي المنتج من الشروط. [شروط Anthropic التجارية](https://www.anthropic.com/legal/commercial-terms)

الميزانية:

- حد لكل PR وحد شهري لكل مؤسسة.
- حجز تكلفة تقديرية قبل الاستدعاء لتجنب تجاوز عدة مهام متزامنة للحد.
- التفريق بين تقدير التطبيق وفاتورة المزود الفعلية.
- إيقاف المراجعة عند نفاد الميزانية، دون تبديل نموذج أو مزود خفية.
- إصدار إعدادات المراجعة وتسجيل النسخة المستخدمة لكل مهمة.

## 12. معايير القبول

| السيناريو | النتيجة المطلوبة |
|---|---|

| تجاوز الميزانية | إيقاف الاستدعاءات الجديدة |

| حذف اتصال أو إزالة التطبيق | توقف المهام المرتبطة عن الاستخدام والنشر |

أهداف تشغيلية للقياس:

- تأكيد استقبال Webhook خلال خمس ثوانٍ بعد حفظ المهمة.

- نشر خمس ملاحظات مهمة كحد افتراضي لكل مراجعة.
- تقييم الجودة على مجموعة PRs موسومة مسبقًا، مع قياس المشكلات الصحيحة والملاحظات الخاطئة والمشكلات التي لم تُكتشف.
- عدم إعلان نسبة جودة تجارية قبل إجراء هذا التقييم.
