## 1. فكرة المنتج

MergePilot بيراجع الـ Pull Requests قبل الدمج، بنفس فكرة CodeRabbit. بيكتب ملخص للـ PR، وملاحظات جنب السطور المعنية، باللغة اللي صاحب المستودع يختارها، والعربي هو الأساس.

**الأساس اللي المراجعة قايمة عليه** (اتعلمناه من تحليل CodeRabbit، §3):

1. **سياق غني قبل النموذج:** التغييرات، والملفات المرتبطة بيها، وقواعد المشروع، والنية من وصف الـ PR والـ issue.
2. **أدوات فحص آمنة** شغالة جنب النموذج.
3. **تحقق من كل ملاحظة قبل نشرها:** الملاحظة اللي مالهاش دليل بتترمي.
4. **حد أقصى للملاحظات:** ٥ ملاحظات مهمة افتراضيًا، أحسن من ٣٠ ملاحظة مالهاش لازمة.

**القيمة اللي بنقدمها فوق الأدوات اللي موجودة:**

- **فهم قواعد المشروع نفسه**، مش بس الأخطاء العامة.
- **تعليقات بالعربي.**
- **اختيار المزود والتحكم في التكلفة.**
- **فحص الأمان والبنية على مستوى المستودع كله.**
- **أفضل ممارسات حسب نسخ المكتبات الفعلية.**

## 2. المستخدمون

| المستخدم | ما يحتاجه |
|---|---|
| صاحب المشروع | يفعّل المراجعة، ويختار المزود، ويحدد الميزانية |

## 3. المراجع المدروسة

### 3.1 CodeRabbit (فكرة المنتج)

اللي CodeRabbit بيعلنه عن نفسه، ومتأكدناش منه بشكل مستقل:

- بيعمل **clone للمستودع جوه صندوق معزول**، معاه توكن مؤقت بس.
- بيبني **خريطة للكود**: الاعتماديات والعلاقات بين الملفات.
- بيجمع **النية** من وصف الـ PR والـ issues والـ PRs اللي قبله.
- بيشغّل **أكتر من ٤٠ أداة فحص** (linters وSAST).
- **وكيل** بيستكشف الكود بأوامر بحث.
- **وكيل تحقق** بيفلتر الملاحظات قبل نشرها.
- بيحتفظ **بذاكرة** للملاحظات اللي الفريق رد عليها.
- بيعمل **مراجعة تدريجية** للـ commits الجديدة.
- فيه **شات** جوه الـ PR.
- الإعدادات في ملف YAML جوه المستودع.

المصادر: [التوثيق](https://docs.coderabbit.ai/guides/code-review-overview)، [المعمارية](https://docs.coderabbit.ai/overview/architecture)، [Cloud Run](https://cloud.google.com/blog/products/ai-machine-learning/how-coderabbit-built-its-ai-code-review-agent-with-google-cloud-run).

**هناخد منه في الإصدار الأول:** السياق، وأدوات الفحص الآمنة، والتحقق، والملخص والتعليقات، والمراجعة التدريجية.  
**مؤجل:** الشات، والذاكرة، ورسومات التسلسل، والإصلاح بضغطة.

### 3.2 DeepSeek Harness وإضافتين للاشتراكات

اتحللت تلات مستودعات محلية في `reference/`. الفولدر ده مستبعد من git، وقريناه قراءة بس من غير ما نشغّل أي حاجة فيه.

| المستودع | طريقة الدخول | الحكم |
|---|---|---|
| `deepseek-harness` (MIT، DeepSeek، نسخة alpha) | API key + OAuth باشتراكات عن طريق مكتبة pi-ai | ✅ **تصميم المزود والأخطاء والمفاتيح ينفع ناخده**. ❌ مسار OAuth بالاشتراك مستبعد |
| `dsh-claude-oauth` (MIT) | OAuth باشتراك Claude، برقم تعريف Claude Code، وبينتحل شخصيته | ❌ مرفوض بالكامل |
| `dsh-plugin-subscriptions` (MIT) | OAuth لخمس اشتراكات، بأرقام تعريف مستلفة وclient secret متسرّب، وبيجمّع حسابات | ❌ مسارات الدخول مرفوضة. ✅ أفكار تجديد التوكن وتصنيف الأخطاء |

**سبب الرفض:** التلاتة بيشغّلوا اشتراكات المستهلكين (Claude.ai وChatGPT) عن طريق إنهم **ينتحلوا شخصية الأداة الرسمية**. ده بيعني رقم تعريفها، والـ headers بتاعتها، والـ system prompt بتاعها، وقراءة ملفات تسجيل الدخول بتاعتها. ده ضد شروط المزودين، وبيعرّض حسابات العملاء للقفل، وبيخلّي المنتج كله يقع في لحظة.

**اللي هناخده (التفاصيل في [ADR-0003](../adr/0003-provider-layer-from-deepseek-harness.md) و[ADR-0004](../adr/0004-policy-gated-oauth-framework.md)):**

- عقد `LlmAdapter`، وفيه دالة إلزامية واحدة بترجّع stream موحّد.
- `LlmFailure`، وفيه أكواد أخطاء ثابتة، وسياسة إعادة محاولة لكل مزود.
- واجهة مفاتيح عمرها ما بترجّع القيمة للواجهة.
- مسار كتابة واحد للمفاتيح، ومعاه قفل.
- `TokenManager` بيجدد التوكن مرة واحدة حتى لو جاله كذا طلب في نفس الوقت.
- تصنيف أخطاء HTTP.

**اللي ناقصهم كلهم:** حساب التكلفة بالفلوس. هنبنيه إحنا.

## 4. شكل التشغيل

```
            ┌──────────── MergePilot Engine (مكتبة) ────────────┐
            │ context · analyzers · providers · review · validate │
            │ publish · budget · credentials · auth(مقفول)        │
            └───────────────┬───────────────────┬────────────────┘
                            │                   │
                 الإصدار الأول               لاحقًا
            apps/action (GitHub Action)   apps/app (GitHub App + سيرفر)
            apps/cli (تشغيل محلي للتجربة)
```

- **الإصدار الأول هو GitHub Action:** جهاز GitHub المؤقت بيشتغل كصندوق معزول جاهز، والمستودع متنسخ عليه. المفتاح محفوظ في GitHub Secrets، فمفيش سيرفر ولا قاعدة بيانات عندنا.
- **بعدين GitHub App:** نفس المحرك، ونضيف حواليه: webhook، وطابور، وقاعدة بيانات، ومفاتيح مشفرة بـ KMS، ولوحة تحكم، وعزل بين العملاء. المتطلبات دي من v0.1 §8 و§10 و§11 لسه سارية على المرحلة دي.

## 6. نطاق الإصدار الأول

### مطلوب

**التشغيل:**

- GitHub Action بيشتغل على `pull_request` لما الـ PR يتفتح، أو يتحدّث، أو يتحول من Draft لجاهز للمراجعة.
- **الفحص الكامل** بيشتغل بإيدنا (`workflow_dispatch`) أو كل أسبوع (`schedule`).
- أداة CLI محلية للتجربة على PR موجود من غير ما ننشر.

**الإعدادات:** ملف `.mergepilot.yml` في المستودع، وفيه:

- المزود والنموذج.
- لغة التعليقات.
- الملفات المستبعدة.
- أقل درجة خطورة تتنشر.
- أقصى عدد ملاحظات.
- ميزانية كل PR.
- ملفات القواعد.
- تعليمات لكل مسار.

**السياق:**

- الـ diff، بكل صفحاته.
- المحتوى الكامل للملفات اللي اتغيرت.
- الملفات المرتبطة بيها.
- ملفات القواعد.
- عنوان الـ PR ووصفه.
- نسخ المكتبات من ملفات الاعتماديات.

**المراجعة:**

- ملخص بالعربي.
- ملاحظات على سطور صالحة، كل ملاحظة فيها: المشكلة، والأثر، والدليل، والإصلاح.
- التركيز على: الصحة البرمجية، والأمان، وفقدان البيانات، ومخالفة قواعد المشروع.

**التحقق:**

- مرور تحقق على كل ملاحظة.
- التأكد إن الملاحظة على سطر موجود فعلًا في الـ diff.
- منع تكرار الملاحظات.

**النشر:**

- مراجعة واحدة بصيغة `COMMENT`، ومعاها علامة مخفية فيها `head SHA`.
- مفيش نشر لو اتعمل commit أحدث.
- مفيش تكرار لو الـ Action اتعاد.

**المراجعة التدريجية:** لما ييجي commit جديد، يراجع الجديد بس.

**الفحص الكامل الدوري:**

- تقرير بالثغرات الأمنية.
- مخالفات البنية والقواعد.
- استخدام قديم أو غلط للمكتبات حسب نسخها.

**الميزانية:**

- تقدير قبل كل استدعاء، ووقف المراجعة لو العدّ هيعدّي الحد.
- حساب التكلفة الفعلية من أرقام الاستهلاك اللي المزود بيرجّعها، وجدول أسعار عندنا.

**المزودين:** الثلاثة بمفاتيح API، ومفيش تحويل خفي لمزود أو نموذج تاني.

**الأمان:**

- فحص الأسرار وإخفاؤها قبل ما أي كود يخرج.
- مفيش تنفيذ لكود الـ PR. ده معناه: مفيش `npm install`، ومفيش linters بتحمّل plugins من المستودع.

### مؤجل

- GitHub App ولوحة التحكم (المرحلة التانية).
- الشات جوه الـ PR والذاكرة.
- رسومات التسلسل.
- الإصلاح بضغطة.
- التعديل التلقائي أو الدمج.
- مقارنة أكتر من نموذج في نفس المراجعة.
- أي OAuth.
- الفوترة نيابة عن العملاء.

## 7. خط المراجعة (Pipeline)

1. **التشغيل:** حدث `pull_request` بيشغّل الـ Action، ونحمّل `.mergepilot.yml`.
2. **قراءة التغييرات:** نقرا الملفات بكل الصفحات. نستبعد الملفات الثنائية والمولّدة والحساسة. لو الـ patch مبتور، الملف ده بيتعلّم «ماتراجعش» ومش بنعدّيه على إنه اتراجع.
3. **بناء السياق:**
   - الملفات اللي اتغيرت كاملة على `head SHA`.
   - الملفات المرتبطة، عن طريق الـ imports والبحث عن الرموز.
   - ملفات القواعد.
   - النية من وصف الـ PR والـ issue.
4. **توثيق المكتبات:** للمكتبات اللي الـ diff بيلمسها، نجيب توثيق نفس النسخة. المصدر لسه قرار مفتوح (§12). اللي بيخرج لمصدر التوثيق هو اسم المكتبة ونسختها بس، ومفيش أي كود.
5. **فحص آمن:** فحص أسرار، وقواعد ثابتة مابتشغّلش كود.
6. **فحص الميزانية:** تقدير التوكنات والتكلفة. لو هتعدّي الحد، نوقف ونكتب سبب واضح.
7. **المراجعة:** استدعاء النموذج ويرجع ملاحظات بشكل منظم (structured).
8. **التحقق:** مرور تاني يتأكد من كل ملاحظة قصاد الكود. بعدها نتأكد من السطر والمكان، ونمنع التكرار، ونرتّب حسب الخطورة، ونقص لحد العدد الأقصى.
9. **النشر:** نتأكد إن `head SHA` لسه هو نفسه، وإن مفيش مراجعة منشورة بنفس العلامة، وبعدين ننشر.

## 8. واجهات المحرك

باقية زي v0.1 §9، ومعاها التعديلات دي:

- **طبقة المزود** بتتبع عقد `LlmAdapter` المأخوذ من Harness ([ADR-0003](../adr/0003-provider-layer-from-deepseek-harness.md)). فوقها `ReviewProvider`، وفيه العمليات: `capabilities` و`validateConnection` و`estimateUsage` و`review` و`normalizeError`.
- **طبقة المفاتيح** هي `CredentialStore`، وليها تنفيذين:
  - في الـ Action: متغيرات البيئة اللي جاية من Secrets.
  - في الـ App بعدين: قاعدة بيانات متشفرة.
  - الواجهة بتشوف بس `CredentialInfo` (موجود / مصدره)، وعمرها ما بتشوف القيمة.
- **طبقة OAuth** فيها `connect` و`status` و`resolveForRequest` و`refreshIfNeeded` و`disconnect`، وكلها **مقفولة افتراضيًا** لحد ما يتسجل اعتماد رسمي.

## 9. الأمان والخصوصية

كل اللي في v0.1 §10 لسه ساري. ومعاه الحاجات الخاصة بالـ Action:

- **`pull_request` مش `pull_request_target`:** PRs اللي جاية من fork مش بتوصلها الأسرار. في الحالة دي MergePilot بيتخطى المراجعة ويكتب سبب واضح.
- **أقل صلاحيات للـ workflow:** `contents: read` و`pull-requests: write`.
- **مفيش تنفيذ لأي حاجة من المستودع.**
- **محتوى الـ PR بيانات غير موثوقة.** أي تعليمات مكتوبة جواه مابتغيّرش السياسة ولا الميزانية.

## 10. الاستضافة والفوترة

- **الإصدار الأول:** المستودع بيشغّل الـ Action على دقايق GitHub، والمفتاح بتاع صاحب المستودع، والفاتورة بتروح له مباشرة.
- **المرحلة التانية:** نرجع للـ SaaS في v0.1 §11 (عزل العملاء، ومفاتيح بـ KMS، وشروط المزودين التجارية).

## 11. معايير القبول للإصدار الأول

| السيناريو | النتيجة |
|---|---|
| PR جاي من fork ومن غير أسرار | الـ Action بيخلص بسلام، ومعاه رسالة «اتخطّينا: مفيش مفتاح» |
| الـ Action اتعاد على نفس الـ SHA | مفيش مراجعة مكررة |
| ييجي commit أحدث وإحنا بنراجع | مفيش نشر للنتيجة القديمة |
| ملاحظة على سطر مش في الـ diff | تتحط في الملخص أو تترمي، ومابتتنشرش على السطر |
| مفتاح ناقص أو غلط | رسالة واضحة باسم المتغير، ومن غير إعادة محاولة لا نهائية |
| تقدير التكلفة هيعدّي ميزانية الـ PR | مفيش استدعاء للنموذج، ورسالة واضحة |
| تعليمات خبيثة جوه الـ PR | ماتأثرش على السلوك |
| سر في الـ diff | بيتخفي قبل الإرسال، وبيتنبّه عليه كملاحظة أمان |
| مخالفة لقاعدة في `CLAUDE.md` | ملاحظة بتشير للقاعدة نفسها |

**الجودة:** نجرّب على مجموعة PRs متعلّمة من مستودع داخلي، ونقيس:

- الملاحظات الصح.
- الملاحظات الغلط.
- المشاكل اللي اتفوّتت.

مفيش أي ادعاء لنسبة جودة قبل التقييم ده.

## 12. القرارات المفتوحة

- **مصدر توثيق المكتبات:** Context7، أو التوثيق الرسمي مباشرة، أو README بتاع npm للنسخة.
- **المزود والنموذج الافتراضي:** بعد اختبار الجودة والتكلفة.
- **الميزانية المستهدفة لكل PR.**
- **مين ينفّذ.**
- **أداة فحص الأسرار:** gitleaks أو مكتوبة جوه المحرك.
- **قواعد Semgrep أو بديلها** للفحص الثابت الآمن.
- **شكل تقرير الفحص الكامل:** issue، أو ملف artifact، أو الاتنين.
